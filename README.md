# Bailey Hall evacuation laboratory

A clean TypeScript implementation of the supplied Bailey Hall mathematical model, with a React/Vite interface and a shared deterministic headless engine. Developed only on `rebuild-from-scratch`; no former simulator source is used.

## Run locally

Requires Node.js 22 or newer and npm.

```sh
npm ci
npm run dev
```

Open the local URL printed by Vite. The interface includes both floors, individual occupants, queue and occupancy colors, stepped-cross-aisle highlighting, geometry provenance, an inspector, public guidance, configurable interventions, and paired experiments in a background worker. Play speed changes animation scheduling, not the integration interval. Configuration changes validate and reset the run. Save a scenario and its seed to replay it.

```sh
npm run typecheck
npm test
npm run build
npm run test:browser
```

Browser tests use installed Chrome on macOS. On another machine set `CHROME_PATH` to your Chrome/Chromium executable. Playwright launches its own local Vite server. Tests do not require an external service or any original simulator.

## Reproducible experiments

```sh
npm run simulate -- --config scenarios/emergency.json --seed 101 --out results/run.json
npm run batch -- --config scenarios/emergency.json --seed 101 --runs 3 --out results/batch.json
npm run batch -- --config scenarios/emergency.json --compare scenarios/concert.json --seed 101 --runs 3 --out results/paired.json
npm run experiments -- --seed 101 --runs 3 --out-dir results/experiment-repeat
```

`experiments` requires a fresh output directory (`--out-dir`, default `results/experiment-sweep`) and refuses to overwrite existing evidence. Configurations are saved under that directory’s `scenarios/`; result files and refinement are written alongside them. The conventional `results/experiments.json` remains historical.

The batch sequence is exactly `seed, seed+1, …`. `experiments` writes all named configurations, three-seed comparisons when invoked as above, and the 0.0125-second refinement of the first emergency seed. Optional `--jobs 4` runs independent policies concurrently without changing their random streams. Run files include the full configuration, seed, engine version, events, exit use, queues, density metrics, accessible progress, and sampled trajectories of aggregate clearance. The experiment sweep omits per-person logs from individual scenario aggregate files to keep them manageable; a single-seed CLI replay regenerates those logs. The refinement file retains both full event logs.

Large result files are versioned as lossless `.json.gz` archives; plain JSON remains available in this workspace and is regenerated by the commands above. Use `gunzip -k results/refinement.json.gz` in a fresh checkout to inspect a full archived log. `npm run archive-results` checks byte-exact round trips and writes a SHA-256 manifest of the source and results. `npm run report` can read either plain or compressed results.

`results/experiments.json` and [the validation report](docs/validation.md) contain the actual evaluated outcomes. A 900-second unfinished run has `clearance: null`, `status: "unresolved"`, and `clearanceBound: "T > 900 s"`. It counts against the 180-second success fraction. An unconditional mean is not reported when any replication is censored. Completed-only quantiles and means are explicitly labelled. Three replications are a smoke-sized exploratory sample, not evidence of operational reliability.

The separate [100-replication Monte Carlo report](docs/monte-carlo-100.md) evaluates the fixed six-manager emergency scenario with fresh audiences and stochastic streams (seeds 1001–1100). Its [CSV](results/monte-carlo-100/replications.csv) retains every replication, including unresolved runs. Full compressed logs and a hash/replay audit accompany the report.

```sh
npm run monte-carlo -- --config scenarios/emergency.json --seed 1001 --runs 100 --jobs 4 --out results/monte-carlo-repeat
node --import tsx scripts/audit-monte-carlo.ts --out results/monte-carlo-repeat
```

The Monte Carlo runner snapshots its configuration and refuses to overwrite existing evidence. Parallel workers change execution speed only; every replication receives its own fresh deterministic seed.

## Literature-based intervention study (engine 1.3.0)

[The updated study report](docs/intervention-study.md) compares five fixed policies on 100 paired fresh audiences each. [The revised PDF](docs/model/Bailey_Hall_Model_Final_Defensible.pdf) includes the literature rationale, current-state route commitment, exact LED and open-belt locations, results and limitations. The original engine 1.0.0 reports above remain historical evidence; the revised study has its own contemporaneous control arm.

```sh
npm run study -- --runs 100 --seed 5001 --configs baseline,coordinated,partial-barriers,dynamic-only,dynamic-partial --out results/intervention-repeat --jobs 4 --selection results/intervention-selection.json
npm run audit-study -- --out results/intervention-repeat
npm run simulate -- --config scenarios/study/dynamic-partial.json --seed 5001 --out results/combined-replay.json
```

The runner archives the source, freezes each policy JSON, checks initial audience identity across policies and distinct audiences across seeds, and stores every full result as compressed JSON. Its source fingerprint must be unchanged when the batch ends. The audit verifies every archive and event hash, reconstructs crossing counts, and exactly replays the first seed for each policy. Repeating the original study must use engine 1.3.0; its source archive accompanies the results. [Development pilots](docs/research/development-history.md) and the frozen selection record preserve unsuccessful alternatives.

The interface includes study presets for coordinated managers, dynamic LEDs, full open partitions, and combined partial/full layouts. The historically preselected experimental combination is **Six managers + dynamic LEDs + partial belts**; it is not an installation recommendation. Exported JSON fully specifies the selected setup. Newly accepted instructions use current reachable routes and local queue information; final exterior crossings are committed.

Generate the figures and paper from preserved results:

```sh
python3 -m venv .tmp/report-venv
.tmp/report-venv/bin/pip install -r scripts/requirements-plots.txt
node --import tsx scripts/export-study-layout.ts --out .tmp/study-geometry.json
.tmp/report-venv/bin/python scripts/plot-study-layout.py .tmp/study-geometry.json
.tmp/report-venv/bin/python scripts/report-interventions.py
.tmp/report-venv/bin/python scripts/report-study-validation.py
tectonic --outdir docs/model docs/model/Bailey_Hall_Model_Final_Defensible.tex
```

`report-interventions.py` accepts an optional study-output directory. The validation report generator uses the preserved refinement/compliance/response experiments. Run the same study runner with `refinement-coarse,refinement-fine` (3 seeds starting at 5001), `compliance-nominal,compliance-low` (20 starting at 6001), or `response-baseline,response-combined` (20 starting at 6001) to reproduce them in a fresh output directory. Those checks do not replace the main fixed-parameter experiment.

## Practical placement and code review (engine 1.3.1)

The [physical placement review](docs/research/placement-review.md) rejects the tested belts and full partitions as installation recommendations: they lack clear incremental benefit and leave door discharge, bases and accessibility unresolved. LED positions are experimental information-exposure locations, not verified local arrows. Independent dynamic devices and fixed staff messages need an agreed, coherent physical guidance plan before any field pilot. The PDF includes a one-page executive summary and the location-by-location assessment.

The [code review](docs/code-review.md) fixes input-validation defects, preserves all LED positions when changing mode, and prevents exploratory sweeps from overwriting evidence. **66 automated tests and 5 browser tests passed**, as did the production build. Five complete first-seed replays matched the historical 1.3.0 results after normalizing only the version label. The 500-run study was not rerun or relabelled. Strict historical source audits still require its archived source.

```sh
node --import tsx scripts/review-replays.ts
```

[Audience encoding](docs/audience-encoding.md) distinguishes exit knowledge from a preference for the foyer. The legacy lecture preset bundles age, response and staffing assumptions; both it and the concert reference originally know all eligible exits. Three new controlled presets in `scenarios/review/` isolate knowledge and entrance preference, without changing age, walking speed or response. A 50% knowledge probability is a sensitivity assumption, not a measured visitor characteristic. They are also available in the interface; no new student-versus-visitor Monte Carlo effect is claimed.

## Model and source hierarchy

The mathematical authority is [the LaTeX specification](docs/model/Bailey_Hall_Model_Final_Defensible.tex). The accompanying PDF, seven-page problem statement, both seating diagrams, and all six reference images were reviewed before implementation. The paper and PDF were revised on 9 November 2026 for the authorized literature-based intervention study. The original manuscript is retained in `docs/model/archive/`.

The engine represents exactly 1,329 audience members: 527 orchestra, 486 mezzanine including three wheelchair places, and 316 balcony. It includes separate recognition and response, adjacent companions, persistent tastes and compliance, finite storage, lane FIFO and service credits, counterflow, locally visible gate delays, manager hearing, static/dynamic signs, projected barrier detours, and two scarce assistance teams. Exterior crossing and street arrival are separate endpoints.

Geometry is a **plan-derived network reconstruction**, not a surveyed CAD model. The drawings establish topology; metric widths, elevations, lane continuity, individual row counts, and wheelchair positions still require venue confirmation. Section totals are exact, but the small seat labels are not transcribed into an authoritative seat inventory. A geometry register exposes every metric assumption, and scenario JSON supports dimension overrides. See [implementation decisions](docs/implementation-decisions.md) for conventions and limitations, including finite-lane return feasibility and external street-time estimates.

The map renders the same graph that the engine traverses. Rows are restricted to their own occupants. The middle stepped connectors lie in an explicit break between orchestra rows and cannot be used by wheelchair users. The emergency elevator, backstage population, and ground-level population are excluded as specified.

## Code map

| Module | Responsibility |
| --- | --- |
| `src/engine/geometry.ts` | Plan-derived geometry, walls, columns, barrier detours, connectivity validation |
| `population.ts`, `rng.ts` | Named streams, audience traits, adjacent groups, fixed preferences |
| `transport.ts` | Gate/headway rates, finite storage, shared continuous lanes, credit accounting |
| `perception.ts`, `routing.ts` | Sightlines, feasible paths, visible gate delays, persistent utilities |
| `guidance.ts` | Public messages, hearing, acceptance, patrols, delayed reports |
| `simulation.ts`, `scheduler.ts` | Fixed-step event ordering, atomic transfers, invariant checks |
| `assistance.ts`, `metrics.ts` | Scarce assistance, separate endpoints, censoring and paired summaries |
| `src/ui/` | React map/controls/inspectors and browser batch worker |
| `scripts/` | Headless runs, paired batches, scenario sweep |
| `tests/` | Unit, full-engine, numerical, reproducibility, and browser tests |

Audience, response, speed and capacity parameters are not adjusted to force the 180-second objective. Intervention layouts are selected on pilot audiences and evaluated on independent audiences. Predictions are conditional on this reconstruction and its uncalibrated assumptions; they are not a fire-safety or building-code certification.
